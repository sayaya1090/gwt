# GWT Gradle Plugin Use Cases

이 문서는 `gwt` 플러그인이 해결하고자 하는 주요 문제 상황과 사용자 시나리오를 정의합니다.

## 1. 개요 (Overview)
본 플러그인은 GWT(Google Web Toolkit) 개발 시 반복되는 설정 작업과 까다로운 테스트 환경 구축을 자동화하는 것을 목표로 합니다.

## 2. 주요 유스케이스

### 2.1 GWT 프로젝트 내 Lombok 어노테이션 활용
*   **사용자**: GWT 엔티티 및 모델 클래스에서 상용구 코드(Boilerplate)를 줄이고 싶은 개발자.
*   **상황**: GWT 컴파일러는 소스 기반으로 작동하므로, 바이트코드를 조작하는 Lombok 어노테이션(`@Getter`, `@Setter` 등)이 적용된 코드를 인식하지 못해 컴파일 오류가 발생함.
*   **해결**: `GwtLombokPlugin`을 통해 GWT 컴파일러가 인식할 수 있는 형태로 소스를 전처리하거나 호환성을 확보하여, GWT 클라이언트 코드 내에서도 자유롭게 Lombok을 사용함.

### 2.2 자동화된 브라우저 통합 테스트 (CI/CD)
*   **사용자**: CI 서버 또는 로컬 환경에서 GWT 로직의 무결성을 자동으로 검증하려는 개발자.
*   **상황**: GWT 코드는 브라우저 환경에서만 동작하므로, 단위 테스트만으로는 한계가 있으며 매번 수동으로 브라우저를 띄워 확인하기 번거로움.
*   **해결**: `./gradlew test` 실행 시, 플러그인이 HTML 호스트 페이지 생성, GWT 컴파일, Ktor 서버 구동을 자동으로 수행하고 Playwright 브라우저를 통해 테스트 결과를 검증함.

### 2.3 개발 모드(DevMode) 연동 및 실시간 검증
*   **사용자**: 기능을 개발하면서 테스트 코드와 UI 동작을 실시간으로 확인하고 싶은 개발자.
*   **상황**: 테스트를 위해 매번 전체 GWT 컴파일을 기다리는 것은 개발 생산성을 저하시킴.
*   **해결**: `gwtDevMode` 태스크를 통해 테스트 소스셋이 포함된 환경을 구동하고, 자동으로 생성된 테스트용 HTML 페이지를 통해 브라우저에서 즉시 로직을 확인 및 디버깅함.

### 2.4 브라우저 내부 로그 및 상태 검증
*   **사용자**: 비동기 통신이나 복잡한 UI 인터랙션 중 발생하는 내부 상태를 검증하려는 개발자.
*   **상황**: 브라우저 내에서 발생하는 `GWT.log()`나 `console.log()`는 일반적인 테스트 도구로 캡처하기 어려움.
*   **해결**: `GwtTestSpec`이 제공하는 로그 수집 기능을 활용하여, 특정 동작 후 브라우저 콘솔에 예상된 메시지가 출력되었는지(`shouldContainLog`)를 선언적으로 검증함.

### 2.5 멀티 모듈 프로젝트에서의 공통 테스트 서버 활용
*   **사용자**: 여러 GWT 모듈이 포함된 대규모 프로젝트를 관리하는 개발자.
*   **상황**: 각 모듈마다 테스트 서버를 각각 띄우면 포트 충돌이 발생하거나 리소스 낭비가 심함.
*   **해결**: Gradle의 `Shared Build Service`를 이용한 `WebServerService`가 빌드 수명 주기 동안 하나의 서버 인스턴스를 유지하며, 여러 테스트 태스크가 안전하게 동일한 서버 인프라를 공유함.
